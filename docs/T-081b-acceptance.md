# T-081b 驗收報告：雙面驗證 + 防回歸檢查

驗收標準由 owner 2026-07-27 於回覆卡 `rc-800a7adb224f` 選項一拍板，取代票面原本的
「跑 audit.py 到低於 3:1 歸零」——後者經實測在**改動前**就已成立，不具鑑別力
（詳見基準線一節）。

判準沿用 T-4527 `audit.py` 第二版的公式：文字／圖示前景用 WCAG 對比度（正文 4.5:1），
非文字元素用明度差 ΔL*（≥ 3.0 才算明確可見）。公式逐行照抄，未自創。

---

## A. 拆分前：單一值能同時滿足兩個用途嗎？

掃過整個 RGB 空間（每軸步進 3，636,056 色），對每個色槽逐色檢查它的兩個用途是否同時達標。

| 色槽 | 淺色主題可行色數 | 內建深色可行色數 | 結論 |
| --- | ---: | ---: | --- |
| `--color-overlay` | **0** | **0** | 🔴 **真的無解**——不存在任何顏色能同時當「淺底上看得見的疊層」與「壓在紅底/綠軌道上的實色前景」 |
| `--color-shadow` | 488,638 | 235 | 有解，但深色主題下的可行區間**極窄**（灰階只有 0~8，共 9/256） |
| `--color-indigo` | 620,668 | 630,449 | 有解，區間寬 |

### ⚠️ 對票面說法的修正（誠實回報）

票面寫「三個色槽**必然打架**」。**實測只有 `--color-overlay` 成立。**
另外兩個找得到可行值——例如 `--color-shadow` 在淺色主題下灰階 68~207 都行。

那為什麼還是要拆？因為**可行 ≠ 找得到**：這三個色槽的聯合約束把可選範圍壓成一條窄縫，
而主題作者看不到那條縫在哪。「精靈村」的作者就踩空了——他把 `--color-shadow` 設成淺色
去救巢狀區塊，代價是全站 `box-shadow` 實質消失。拆開之後，每個用途各自選值，
不再需要有人猜中那條縫。

⇒ **`--color-overlay` 是修 bug；另外兩個是移除陷阱。** 兩者都值得做，但理由不同，
不該用同一句「必然打架」帶過。

## B. 拆分後：所有約束能同時滿足嗎？

給定兩份具體主題，逐項實算（`after_split_proof.py`）：

**淺色主題（每個新槽各自挑值）——8 項全數通過**，含票面點名的三個痛點：
未讀數字 6.01:1、燈箱關閉鈕 14.48:1（拆分前是 1.45:1）、捲軸拇指 ΔL* 41.54、
投影 ΔL* 16.91、下沉表面上的正文 6.88:1。

**內建深色主題（7 個新槽＝預設值，像素不變）——8 項通過 7 項**。

### 唯一未達標的一項是既有問題，不是本次造成

`--color-on-danger`（白）壓在 `--color-danger`（`#f0736b`）上 = **2.85:1**，低於正文門檻。

這是**內建深色主題本來就有的**：拆分前該處用的是 `--color-overlay`（同樣是白）壓在同一個
紅底上，數值一模一樣。本次改動保證像素不變，因此也原封不動地保留了這個既有缺口。
**不在本票範圍內修**——修它會改變內建主題的外觀，與「像素不變」的驗收條件直接衝突。
已列為待 owner 決定的獨立事項。

## C. 防回歸檢查

`frontend/scripts/check-token-roles.mjs`，經 `npm run lint:token-roles` 執行，
已接進 `bin/ci.sh`（步驟 4b0b，緊接在既有的 css colour-token lint 之後）。

它釘住的不變量是「每個原色槽只剩一種語法形式」：
`--color-overlay` 只能出現在**真的半透明**的 `color-mix(..., transparent)` 裡；
`--color-shadow` 只能餵 `box-shadow`；`--color-indigo` 不得用於捲軸。另外檢查 7 個新槽
仍然存在、且仍有人使用（沒有被整批改回去）。

⚠️ **round-2 修正了其中一條規則**：原本還檢查「新槽不得 alias 回母槽」，但那條的前提是錯的
——alias 只是**預設值**，主題明寫該槽就仍然分得開，而 alias 正是既有淺色主題包不被弄壞的
唯一辦法（見拆法定案書 §3.5）。該條已移除，其餘兩條（呼叫點改回母槽、新槽沒人用）不變,
它們才是真正的「合併回去」。同時補上三種原本可繞過的寫法。

## D. 基準線與 audit.py 的處置

改動前以 audit.py 第二版跑過（`baseline-report.txt`）：源自本票三個色槽的「低於 3:1」
組合**已經是 0**，故該標準無鑑別力。兩個原因均查證：(1) 票面引用的 1.09/1.11 是第一版
的比值，而第二版自己認定比值對非文字元素是錯的量尺；(2) 第二版的掃描條件
（要有 `color:` ／要是 border 或 `:hover`）把捲軸與下沉表面兩類規則整個跳過。

T-4527 表示會再出第三版（改用 CIEDE2000、納入實色背景）。本報告的結論**不依賴** audit.py
的任一版本——A、B 兩節都是獨立實算。

**改動後重跑（輔證，2026-07-27）**：T-4527 卡上釘的 audit.py 屆時仍是**第二版**
（`att-f5e097262dd0`，sha256 前 16 碼 `d951a3e89d2b28e6`，無 CIEDE2000），所以就用第二版跑，
並如實聲明它無鑑別力。輸出 `docs/T-081b-evidence/audit-after-report.txt`：

| | 改動前（baseline） | 改動後 |
|---|---|---|
| 抽出真實配對 | 163 組 | 146 組 |
| < 3.0:1 | 2 組（皆 `--color-on-accent` 勾選框勾） | **同樣那 2 組** |
| ΔL* < 1.0 | 2 組（皆 `--color-card`） | **同樣那 2 組** |

⇒ 兩項不合格**在改動前後完全相同、且都與本票的三個色槽無關**：本次拆分**沒有引入**
任何新的低對比組合，而票面原本的「歸零」標準在改動前就已成立（見上）。配對總數下降是
拆槽把原本共用一個名字的規則分流到不同 token 所致，不是規則變少。

## F. 既有主題包相容（round-2 追加，原本漏掉的一半）

驗收判準只要求「內建主題像素不變」，那只證明了**沒有主題包**時的樣子。獨立審查指出
真正會炸的是**已經匯入的主題包**：一份 T-081b 之前寫的淺色包只認得舊名字，拆槽後被搬走
的呼叫點改讀新槽，新槽在包裡不存在。原本的字面預設值會讓它靜默退回內建深色值。

修法（預設值改 alias，見拆法定案書 §3.5）之後實測：

| 探針 | base（origin/main） | head（本分支） |
| --- | --- | --- |
| webhook 未讀數字 `color` | `rgb(0,0,0)` | **相同** |
| webhook 送出鈕 `color` | `rgb(0,0,0)` | **相同** |
| 開關滑塊 `background` | `rgb(0,0,0)` | **相同** |
| 燈箱關閉鈕 `color` | `rgb(0,0,0)` | **相同** |
| 頁籤未讀徽章 `color` | `rgb(0,0,0)` | **相同** |
| webhook 請求詳情底 | `srgb 0.8 0.8 0.8 / 0.14` | **相同** |
| 分享鈕底 | `srgb 0.8 0.8 0.8 / 0.55` | **相同** |

同一組探針在**不帶任何主題包**（內建深色）時 base 與 head 也逐一相同。
腳本與輸出：`docs/T-081b-evidence/legacy-pack-compat.mjs` / `-report.txt`。

⇒ 驗收判準本身少了這一條。**「內建主題像素不變」不等於「既有主題包不變」**，
拆 token 時後者要另外證，而且只有它會直接炸到使用者。

# 定期訊息（scheduled message）— T-f059

一條排程到期時，server 把一則**預先寫好的訊息**送給一位成員（正職或外包），
走的是**現有聊天訊息那一條路**：在線即時收到、離線進持久信箱等下次上線、
由收件的 agent 自己決定何時處理。owner 2026-08-10 對投遞語意的原話是
「不能跟現有聊天機制一樣就好嘛」——所以這裡**不發明新的投遞語意**。

它是「回呼端點（webhook）」的孿生兄弟：webhook 把觸發者放在外部系統，
定期訊息把觸發者換成**時鐘**，其餘完全相同。

## 為什麼不做成「定期開票」

那會把「排程」跟「排程的其中一種用途」綁在一起。定期送一則訊息是**更小、更通用的原語**：
提醒、巡檢、盤點都用得上，而收到訊息的 agent 若判斷該開票，它自己就會開。

⚠️ **這個形狀有一條天然界線**：訊息送出去之後，「他做了沒」在畫面上看不到，
除非他自己開了票。**這不是缺陷，是選擇。** 哪天發現「排程有送、事情沒發生」，
那就是把某幾種用途升級成開票的訊號。

## 資料模型

`scheduled_message`（migration `00050_scheduled_message.sql`）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `id` | TEXT PK | `sch-` + 12 hex |
| `member_id` | TEXT | 收件者。**可以是正職，也可以是 `ow-` 外包**（見下方「收件對象」）。**不下外鍵**（照 00001 decree） |
| `label` | TEXT | 給人看的名稱；也放進 meta，讓收件端知道是哪一條 |
| `body` | TEXT | 要送出的訊息內容 |
| `cadence` | TEXT | `daily` / `weekly` / `monthly`（CHECK 閉集） |
| `day_of_week` | INTEGER | weekly 用，0=週日 … 6=週六 |
| `day_of_month` | INTEGER | monthly 用，**1–31**（見下方「不存在的日期怎麼辦」） |
| `hour` / `minute` | INTEGER | 0–23 / 0–59 |
| `timezone` | TEXT | IANA 時區名，預設 `Asia/Taipei` |
| `status` | TEXT | `enabled` / `disabled`。**是撤銷開關、不是生命週期**；`DELETE` 才是永久移除 |
| `last_fired_slot` | TEXT | 🔴 **已送出的那個時間槽的識別字串**（見下） |
| `last_fired_ts` | REAL | 上次真的送出的時刻（給人看的，不參與判定） |
| `created_ts` | REAL | epoch secs |

索引：`idx_scheduled_message_member ON scheduled_message (member_id)`。

### `day_of_month` 不存在的日期怎麼辦：**整個月跳過**

**owner 2026-08-10 裁定（卡 `rc-aeef15360ab5`，選②）：開放 1–31，照通用標準辦。**

29／30／31 在某些月份不存在。做法有三種：跳過那個月、夾到當月最後一天、或乾脆把範圍砍到 1–28。
**這裡採第一種**，也就是 iCalendar RFC 5545 對「無效的重複日期」的規定：
那一次**不算進重複集合**，既不報錯也不改成別的日期。

⚠️ **這條的已知代價，寫在這裡是為了不讓下一個人以為它是 bug**：
設 31 號的排程**一年只會發生七次、二月永遠不發生**，而且沒有任何東西會叫。
這是**知情後選擇接受**的行為，不是漏考慮——提案時建議的是「1–28 ＋ 一個『每月最後一天』選項」
（RFC 5545 用 `BYMONTHDAY=-1` 表達同一件事），owner 選了與通用標準一致的那條。

🔴 **實作上的連帶要求**：算「現在之前最近的一個時間槽」時，**不能只往回看一個月**。
`day_of_month = 31`、現在是 3 月 1 日，三月的 31 號還沒到、二月根本沒有 31 號，
最近的一個槽是 **1 月 31 日**——要往回兩格。
往回找要能跨過沒有那一天的月份（實作上設一個有界的回看上限，`monthlyLookbackMonths = 12`；
找不到就視為沒有槽）。**只往回看一格的寫法會靜靜地漏掉，而且測試若只用 1–28 的日期永遠不會紅**
（那個上限本身也一度沒有任何測試守著：改成 1 整包還是綠的，現在由
`TestMostRecentSlotSkipsMonthsWithoutTheDay` 的「3 月 1 日」那一段釘住「至少兩格」）。

### 🔴 DST 往前跳、當地**時刻**不存在怎麼辦：**往後挪，不跳過**

「這個月沒有那一天」**不是**這裡唯一一種「不存在」。另一種是**那一天在、只是少了一小時**——
DST 往前跳吃掉的那段牆上時刻。**兩者的處置刻意不同：**

| 不存在的東西 | 處置 | 理由 |
|---|---|---|
| **日期**（2 月 31 日） | **跳過那一次** | owner 卡 `rc-aeef15360ab5` 裁定，RFC 5545。使用者要的那個「日子」這個月**根本不存在**，挪到任何一天都是挪成**別的日子** |
| **當地時刻**（DST 跳掉的那一小時） | **往後挪到第一個存在的時刻** | 日子在、只是短了一小時。**跳過＝那天使用者什麼都沒收到，而且沒有任何東西會叫**——那正是這張票要消滅的失敗模式。晚一小時是晚，不是靜默 |

例：`America/Havana` 在 2026-03-08 00:00 直接跳到 01:00，那天**沒有 00:30**。
一條「每月 8 號 00:30」的排程，2026 年三月那一次**在 01:00 發生**（不是消失）。
`America/New_York` 2024-03-10 沒有 02:30，一條「每天 02:30」那天**在 03:00 發生**，
而**隔天回到 02:30**——挪動只影響那一次，**不會永久飄移**。

> 這與公司內 `svc-automation`（`src/triggers/time_based/scheduled/arming.py` 的
> `_first_existing_instant`）採同一條規則：每次 +1 分鐘往後找、上限 120 分鐘。
> 這裡的上限同樣是 120 分鐘（`dstGapScanMinutes`）：tz 資料庫裡的 gap 從來不超過一小時
> （Lord Howe 只有半小時），而這個上限順帶讓**整個日曆日被刪掉**的情形
> （`Pacific/Apia` 1994／2011 的換日線位移）自然落回「這一天沒有槽」，往前一天再找。

⚠️ **實作上「讀回來比對」不是可有可無的檢查**：Go 的 `time.Date` 碰到不存在的牆上時刻
**不會報錯，而是正規化到別的時刻**，而且**兩個方向都會**——
`Havana 2026-03-08 00:30` 會被推**回** 03-07 23:30（日期都變了），
`Australia/Lord_Howe 2026-10-04 02:15` 會被推**前**到 02:45（**年月日時全對，只有分鐘晚了 30 分**）。
所以：**候選時刻要把 年/月/日/時/分 全部讀回來比對**，只比日期會讓後者靜靜地送晚半小時；
而且**要往後挪就自己挪、不能撿 `time.Date` 正規化的結果**（Lord Howe 那例正確答案是 **02:30**，
不是 Go 隨手給的 02:45）。

## 🔴 排程游標：存「時間槽」，不是存「上次執行時間」

`last_fired_slot` 存的是**那一格的識別字串**，例如 `2026-08-10T09:00+08:00`。

每個 tick：
1. 依 `cadence` / `day_of_*` / `hour` / `minute` / `timezone`，算出**現在之前最近的一個到期時間槽**。
2. 那個槽**若嚴格晚於** `last_fired_slot` 所指的那一刻 → 送出，然後把它寫回 `last_fired_slot`。
3. 否則（相等、或更早）→ 什麼都不做。

🔴 **第 2 步比的是「時序」不是「字串不等」，這一點是有代價換來的。**
初版寫的是「字串 ≠ 上次就送」，而那不是同一個問題的答案：
「跟上次不一樣」包含了**比上次早**。整套設計其實隱含依賴一件從來沒有人保證、也沒有人檢查的性質——
**算出來的槽必須隨 `now` 單調遞增**——而那個性質**在交付時就是假的**：
`America/Santiago`（午夜往前跳）算出來的槽會往回跳一格，於是兩則已經送過的訊息又送了一次。
（詳見上面「當地不存在的時刻」與 `schedule_slot.go` 的 `dayAnchor`。）

把判定換成「嚴格晚於」，游標就變成**棘輪**：只進不退。
往後就算某個時區又讓槽的計算出現非單調的抖動，最壞也只是**少送一次**（可發現），
而不是**重送**（不可發現）。這是**防線，不是證明**——真正的證明在 DST 測試裡。

🔴 **但「嚴格晚於」單獨一層是不夠的，另一半是「槽必須用構造的」。**
秋季往回撥那天，**同一個牆上時刻會出現兩次**，而那是**兩個不同的瞬間**——
第二個確實嚴格晚於第一個，光靠時序比較**擋不住**。
擋住它的是另一個性質：**槽一律由 (年,月,日,時,分,時區) 構造出來，絕不從 `now` 的位移推導**，
所以重複時段的兩次都算出**同一個瞬間**、渲染成**同一個槽字串**，第二次就不嚴格晚於游標。
`America/New_York` 2026-11-01 的 01:30 排程有一條逐分鐘走過整段重複時段、**恰好送一次**的測試釘住這件事。
（`svc-automation` 在 `test_ace10966_round_supersession.py` 的註解也記了同一課：
它們是靠當地 (date, slot) 識別字串的碰撞擋掉那一格的，**兩層都要**。）

🔴 **第三層：編輯永遠不碰游標那兩欄。**
`PATCH` 是**讀出整列 → 改幾個欄位 → 寫回**，而 tick 每 60 秒推進同一列的游標。
只要 tick 落在那個「讀」與「寫」之間，整列寫回就會把**已經送出去的事實**倒回「還沒送」，
下一個 tick 再送一次。**這一層是「嚴格晚於」救不了的**——被倒退的是游標本身，
新算出來的槽對倒退後的游標而言**確實**嚴格晚於。
所以編輯走 `UpdateScheduledMessageSettings`：`UPDATE` 的 `SET` 清單裡**根本沒有**
`last_fired_slot` / `last_fired_ts`（**不是寫回原值，是不寫**），tick 併發推進的結果因此活得下來。
需要動游標的只有 re-aim 那一條路，它明講地走 `AimScheduledMessageCursor`，而且是**往前移**、與單調性一致。
（`last_fired_ts` 連 re-aim 都不寫：它記的是「真的送出去的時刻」，重新對準不是一次投遞。）
回應改成**寫完之後重讀那一列**，免得 wire 上出現一個資料庫裡並不存在的游標值。
> 這正是 `MarkScheduledMessageFired` 註解早就寫過的那件事的**鏡像**：
> 那一側說「tick 不要拿快照整列 re-put，會蓋掉 owner 的編輯」，
> 而編輯這一側原本沒有對應的防護——同一個競態的另外一半。

⚠️ **我們仍然沒有的一層，寫在這裡以免下一個人以為有**：`svc-automation` 另外有一道結構性防線——
以「這一輪」為唯一鍵的條件寫入，寫不進去就代表這一輪已經跑過。**本包沒有這一層。**
理由：那一層防的是**多個 ticker 併發**跑同一條排程，而這裡的 tick 是
**單一 process、單一 goroutine**（`startScheduledMessageCadence` 只掛一顆），
同一條排程不可能被兩個 tick 同時處理。⇒ **哪天 server 變成多副本、或 tick 改成並行，這一層就必須補上**，
因為到那時「嚴格晚於」是讀後寫、擋不住兩個併發的 tick 各自讀到同一個舊游標。

三個驗收條件由這個形狀承載（**不是「構造上為真」**——那個說法太強，見下）：

- **server 重啟不重送同一次** —— 重啟後重算出同一個槽字串，比對相等就跳過。
  不依賴任何「上次跑到哪」這種活在記憶體、換版就遺失的狀態。
- **錯過的不補送** —— 永遠只看「最近的一個槽」。停機三天，上線後只補送最近那一格，
  不會一次湧十則。
- **剛建立的排程不會當場就送** —— 建立時 `last_fired_slot` 初始化成**建立當下的最近一個槽**，
  所以早上十點建一條「每天 09:00」不會立刻送出今天的那一則。

> 反例，別抄：`receipt_watch.go` 的 `armReceiptWatch` 把 deadline 放在記憶體 map 裡，
> 重啟即遺忘。那個取捨在它自己的檔頭有寫明，但**排程游標不能這樣做**——
> 重送的樣子跟正常送出一模一樣，沒有任何東西會叫。

⚠️ **「構造上為真」這個說法本身是這一票學到的教訓，留著當紀錄。**
初版在 migration 註解、凍結 spec 與這份文件三處都寫了
「這三條**構造上為真**、不靠小心」。那太強了：**存槽這個形狀本身什麼都不保證**，
三條全都架在「槽的計算隨 `now` 單調遞增」這個**沒被寫下來、也沒被檢查**的前提上，
而那個前提**交付當下就是假的**。一句寫在凍結契約裡的現在式斷言，
比一個已知缺口更危險——讀的人不會再去查。現在三處都改成**描述機制**（棘輪＋構造式的槽），
並指向釘住它的測試。

## 收件對象：正職與外包都可以

⚠️ **不要用 `resolveMember`**（`api_helpers.go`）：它**明確排除 `kind == outsource`**，
所以今天 webhook 端點根本綁不到 `ow-` worker。

聊天可以送給外包（`resolveChatRecipient` 同時允許 `KindAssistant` 與 `KindOutsource`），
而定期訊息就是一則聊天訊息 ⇒ **用聊天那一套的收件者判準**。

⚠️ **一句實話**：外包 worker 綁一張任務、任務結束就作廢。掛在外包身上的排程
**會跟著那個 worker 一起消失**。這是外包這個角色的性質，不是本功能的缺陷。

## 投遞：收件端怎麼分辨這是定期訊息

完全對稱 webhook 的做法：

| | webhook | 定期訊息 |
|---|---|---|
| 寄件者 | `hook:<endpoint_id>` | `sched:<schedule_id>` |
| meta | `meta.webhook = {endpoint_id, purpose}` | `meta.scheduled = {schedule_id, label, slot}` |

`chat_message.meta` 是 open map（TEXT 欄存 JSON、`newChatMessageDTO` 原樣上 wire），
新增 key 不必改 schema。系統裡的合成寄件者原本只有兩個先例：`hook:` 與 `system`。

⚠️ **server 端不讀 `meta.scheduled`**，跟 `meta.webhook` 一樣——它純粹是給收件的 agent 讀的。

⚠️ **`body` 沒有 4,000 字上限，而 `post_chat` 有。** 那道 cap（`chatBodyMaxChars`）掛在
`POST /api/chat` 的 handler 上，不是掛在寫入上；`deliverScheduledMessage` 跟 webhook ingest
一樣直接寫 `ChatMessage`，所以繞過它。這與 webhook 是同一個形狀、不是本功能新開的洞，
但 `api_chat.go` 那段註解原本**列舉**了兩條豁免路徑（owner 與 `hook:*`），本包加了第三條
而沒有任何東西會叫——所以那份列舉已換成一條可執行的查詢
（`grep -n 'msg := ChatMessage{' server/ocserverd/*.go`）。

## 對外介面

四條 REST，全部 `MCPExclude`（**不新增 MCP 工具**）：

| Method | Path | 說明 |
|---|---|---|
| GET | `/api/members/{member_id}/scheduled-messages` | 列出這位成員的排程 |
| POST | `/api/members/{member_id}/scheduled-messages` | 新增一條 |

| DELETE | `/api/members/{member_id}/scheduled-messages/{schedule_id}` | 永久移除 |

`Auth: gated`、`Requires: admin_agent` —— 與隔壁 webhook CRUD 同級，
也就是 owner 與 admin 助理設得動。

**為什麼不上 MCP 工具面**：既有先例就是這樣——webhook 的四個 CRUD 全是 `MCPExclude`，
只有除錯用的 `list_webhook_requests` 上了工具面。**設定類 CRUD 走座艙，不走工具目錄。**
（webhook CRUD 升到 `admin_agent` 的理由是它的 DTO 帶明文 token；
定期訊息的 DTO **不帶任何祕密**，門檻同級是為了與鄰居一致，不是因為有祕密。）

### DTO 欄位

`ScheduledMessageDTO`（回應）：
`id` · `member_id` · `label` · `body` · `cadence` · `day_of_week` · `day_of_month` ·
`hour` · `minute` · `timezone` · `status` · `last_fired_slot` · `last_fired_ts` · `created_ts`

`ScheduledMessageCreateDTO`（POST body）：
`label` · `body` · `cadence` · `day_of_week` · `day_of_month` · `hour` · `minute` · `timezone`

**必填：`body` · `cadence` · `hour` · `minute` · `timezone`。**
為什麼把時刻與時區也列進必填，而不是給它們一個預設值：
- 一條**沒有時刻**的排程沒有意義，讓呼叫端省略它只是把「幾點送」這個問題推給一個沒人裁定過的數字。
- **時區更關鍵**：一旦允許省略，那個預設值遲早會被讀成「server 所在的時區」，
  而那正是 D2 要消除的東西。逼呼叫端明講，這個歧義在介面層就不存在。

🔴 **「必填」不等於「擋住了」——`Local` 與空字串要另外明文拒絕（422）。**
`time.LoadLocation` 對這兩個名字**都會成功**：`"Local"` 回**主機所在時區**、`""` 回 UTC。
所以「載得動就放行」這個判準**擋不住真正危險的那兩個**——它們把「幾點送」的答案
交給**部署細節**（機房位置、`/etc/localtime`），而那恰恰是逼填時區想消滅的東西。
初版就是這樣：`{"timezone":"Local"}` 回 **200**，游標用主機時區算。
現在 `ValidateScheduledMessageTimezone` 直接點名拒絕這兩個；`UTC` 本身是一個明講的時區，**放行**。
⚠️ **寫入路徑與 tick 路徑兩層都擋**：`runScheduledMessageTick` 每一列都再驗一次，
因為舊列（規則生效前寫入的）與直接改 DB 都繞得過寫入路徑，而 tick 是最後一道有人看的地方。
那道守衛**不是重複碼**——`mostRecentSlot` 只做 `LoadLocation`，對 `Local` 是會算出槽的；
拿掉 tick 那段守衛，`TestRunScheduledMessageTickRefusesAHostRelativeTimezone` 就會紅。

其餘三欄維持選填，**而且它們的 fallback 寫在各自欄位的 `description` 裡**（不另外編一份清單）：
`label` 省略＝沒有標籤；`day_of_week` 省略＝0（週日），只有 `weekly` 會讀它；
`day_of_month` 省略＝1，只有 `monthly` 會讀它。

`ScheduledMessageUpdateDTO`（PATCH body）：以上每一欄都是 **optional**（照憲章 §12「對外 DTO 加欄一律 optional」），
只送要改的那幾欄；`status` 也在這裡，用來啟用／停用。

## 座艙：一張卡，長在兩個面板上

`ScheduledMessagesCard.tsx` 一個元件，由 `AgentDetailPanel` 的 `extraExpandCards` 槽
**同時**被正職 wrapper（`MemberDetailPanel`）與外包 wrapper（`WorkerDetailPanel`）呼叫。
不複製 JSX 的理由跟收件者判準同一條：排程可以綁在 `ow-` worker 上，所以兩邊都要有；
而 webhook 今天只長在正職那一套，正是「複製一份就開始各自漂移」的同一個形狀
（`WorkerDetailPanel` 在本票之前**根本沒有任何 `extraExpandCards` 呼叫端**）。

### 游標怎麼呈現：卡片顯示「上次送出時間」，不顯示槽的識別字串

**現況（本票交付的樣子）**：每一列在內容底下有一行「上次送出」——
送過就是人看得懂的絕對時戳（沿用 repo 既有的 `formatAbsolute`），沒送過就是「尚未送出」。
兩個方向各有一條測試，並用 mutant 驗過紅的是對應那一條。

`last_fired_slot`（槽的識別字串）**仍然上 wire、但不顯示在畫面上**——它是給需要推理游標本身的呼叫端用的，
不是給人讀的（`2026-08-10T09:00+08:00` 對使用者沒有意義，對「有沒有送過」的判定才有意義）。

> **這一段的歷史，留著是因為它示範了一個容易自欺的形狀。**
> 初版的 spec description 寫著回應帶 `last_fired_slot`「so the panel can show exactly where
> the cursor stands」，而當時那張卡**一次都沒有 render 過它**——一句現在式的假話，
> 住在一份已經凍結、而且 owner 過目過的契約裡。
> 文件對質那一輪**沒有**把它窄化掉（窄化會讓不一致消失在文字裡，比留著缺口更糟），
> 而是把缺口寫明留給裁定。
> 處置分兩步，順序有意義：**先讓現實符合承諾**（卡片真的顯示上次送出），
> **再把那句話收斂到現況**（區分「畫面顯示時戳」與「欄位供呼叫端推理」）。
> 只做第二步就是抹平；只做第一步則會留下一句仍然不精確的話。

## 背景迴圈

照這個 repo 既有的形狀（`reconcile.go` / `auto_update.go`）：
`startScheduledMessageCadence(period)` 只負責掛 goroutine，
**一個 tick 拆成獨立可測的 `runScheduledMessageTick(now float64)`**，
測試直接呼叫 tick、不等時鐘。間隔 60 秒（與 auto-update 同級；
最小排程粒度是「分鐘」，60 秒足夠）。

與既有五支 cadence 一致：sleep-then-tick、沒有 `time.Ticker`、沒有 context cancel。

## 實作時才浮出來的三個決定（設計初稿沒講，在這裡補上）

### 1. 改設定時，游標會不會重新對準？——**動到時間才對準**

`PATCH` 動到 `cadence` / `day_of_week` / `day_of_month` / `hour` / `minute` / `timezone`
任一欄時，游標重新種到**當下**那個槽。
理由：中午把「每天 09:00」改成「每天 08:00」，不重新對準的話會**當場補送今天的 08:00**——
使用者只是改了設定，不預期它立刻說話。

反過來，只改 `label` / `body` / `status` **不動游標**。
理由：`status` 也算的話，**停用再啟用就會靜靜吞掉下一則**——而那看起來完全正常。

🔴 **判準是「值有沒有變」，不是「欄位有沒有出現在 body 裡」。**
初版用的是後者，於是一個 `PATCH {"hour":9}`（**值根本沒變**）也會重新對準游標。
今天座艙的卡片沒有編輯時間的 UI 所以碰不到，但**任何把整張表單一起送出的呼叫端**
（＝遲早會有的「編輯」按鈕）會在**每一次存檔**時重新對準；
只要那次存檔落在「槽剛過、下一個 tick 還沒到」的那 60 秒窗口裡，**那一則就被永久吞掉**，
沒有錯誤、沒有 log、卡片上完全正常。所以現在是**拿新值跟 DB 裡的舊值逐欄比對**，真的變了才對準。

⚠️ **「不動游標」是字面上的不動**：不重新對準的那條路，`UPDATE` 語句裡連
`last_fired_slot` / `last_fired_ts` 都沒有。把讀出來的原值再寫回去**不等於不動**——
tick 可能在「讀」與「寫」之間推進了它，寫回原值就是把一次已經發生的投遞倒回「還沒送」。
理由與機制見上面「排程游標」那節的第三層。

### 2. 收件者也可以是 owner 本人

這是「照抄聊天的收件者判準」的直接後果（那條規則本來就允許 owner）。
**接受**：定期提醒 owner 本人是合理用途，而且刻意排除它需要一條只為這裡存在的例外。

### 3. 收件者已經不在了 → **跳過，而且不推進游標**

游標的語意是「**這個槽已經送出去了**」。替一個沒送成功的槽寫上游標，
等於把一次失敗洗成一個事實。所以那一輪什麼都不寫，只留一行 log。

⚠️ **已知代價**：一條排程的收件成員被移除之後，它會**每一次 tick 留一行 log**（每分鐘一行），
直到有人把那條排程刪掉。這是刻意的——那行 log 描述的正是真實情況（有一條排程指向一個不存在的人）。
要消掉噪音的正解是**在成員被移除時一併收掉他的排程**，那是另一張票的範圍，不在本包。

## 這個功能對現有 agent 是隱形的

本包**不動 `seeds/`**（票面範圍邊界；另一條 seeds 規則衝突正等 owner 裁定）。
連帶結果：agent 收到 `sched:` 開頭的訊息時，開機說明裡**沒有任何一段告訴他那是什麼**。

⚠️ 這與 webhook 那一段（`seeds/system_interaction.md` §4.2）的差別要講清楚：
那一段的主要工作是教「**外部不可信輸入**的用途守衛」，
而定期訊息是 owner／admin 在座艙裡自己設的，**不是外部不可信輸入** ⇒ 那條守衛的理由不轉移。
剩下的缺口只是「不認得這個寄件者」，而訊息內容本身就會說明要做什麼。
